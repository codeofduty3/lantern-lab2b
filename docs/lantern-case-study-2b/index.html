This codelab follows one quarterly SEC Business Development Company (BDC) release from its monthly ZIP files to a reproducible holdings panel, an evidence-based reconciliation report, a read-only API, and a browser UI.

By the end you will be able to:

  • Explain how SUB, TAG, NUM, and SOI describe the same filing.
  • Collapse multiple SOI facts into one investment while preserving source rows.
  • Apply structural cleaning rules without tuning them to the filed total.
  • Reconcile holdings to each fund's disclosed fair value.
  • Test a sample against the human-readable filing on SEC EDGAR.
  • Rebuild every output with DVC and consume it through a separate UI and API.

The release used here is 2026q3, assembled from the SEC monthly files 2026_07, 2026_08, and 2026_09. The panel deliberately excludes cash and money-market lines because they are not borrower investments.

Goal: restore the three raw SEC files and prove that their hashes match the committed manifest.

Install the project once:

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Restore the DVC-tracked raw release:

dvc pull

Inspect the release configuration and manifest:

cat params.yaml
cat data/manifest.json

Expected configuration:

release: 2026q3
release_months: 2026_07, 2026_08, 2026_09
use_fixture: false

The manifest records one SHA-256 per monthly ZIP. scripts/acquire.py downloads, unpacks, verifies, and combines those files into data/raw/2026q3_bdc/. Raw data belongs in DVC, not Git.

What could go wrong: a stale manifest or an interrupted download will fail the hash check. Do not bypass that check; remove the bad DVC checkout and run dvc pull again.

Positive : A valid release has 182 SUB rows and 197,160 SOI rows before period filtering.

Goal: turn long-form XBRL facts into one current-period holding per filing and investment identifier.

Run the parse stage:

dvc repro parse

Inspect what the stage printed. The verified release has:

  • 182 filings in SUB;
  • 101,220 current SOI rows;
  • 68,175 candidate holdings after coalescing;

Inspect one source row:

python - <<'PY'
import yaml
from src.lookthrough import load, mapping, paths

params = paths.load_params(".")

The important provenance rule is that source_rows retains every original SOI row. A coalesced holding is still traceable to the machine evidence that created it.

What could go wrong: summing every SOI date mixes comparative schedules into the current period. holdings.split_periods compares each row date with the filing period from SUB.

Goal: remove totals, duplicated issuer summaries, and liquidity lines using signals visible in the row itself.

Run:

dvc repro clean

Open reports/cleaning_log.csv and docs/cleaning_log.md.

The rules run in this order:

  1. rule_totals removes explicit total, subtotal, and category-only labels.
  2. rule_issuer_aggregates removes a short issuer row when a detailed instrument row for the same issuer also exists in that filing.
  3. rule_cash removes explicit cash and money-market lines.

Coverage is calculated after each rule for reporting, but it never selects a pattern or changes the rule order. In the verified release the reported dollar coverage moves from 27.1% before the three structural rules to 28.8%, 40.0%, and then 42.1% after cash exclusion.

Inspect the logged examples:

python - <<'PY'

PY

What could go wrong: a rule tuned to one fund's reconciliation gap will break another filing. Each rule's motivation must make sense from the identifier structure alone.

Negative : Cash is excluded uniformly. A filer that includes cash in its filed total will remain outside tolerance and must be triaged with evidence.

Goal: compare every attempted filing with its own undimensioned InvestmentOwnedAtFairValue fact and retain every exclusion.

Inspect the outputs:

  • outputs/panel/holdings.parquet contains 33,222 investment holdings.
  • reports/coverage.csv contains one row for every attempted filing.
  • reports/coverage.json is the DVC metric used by the API.
  • reports/triage.md explains every exclusion.

Every summary number must include both filing coverage and dollar coverage. Filing counts alone make a small admitted filing look equivalent to a large one.

What could go wrong: building the reconciliation universe from the panel drops filings with zero identifiable holdings. The implementation starts from all filings with SOI rows and explicitly reports the five filings with no SOI rows.

Goal: test whether panel values match the filing narrative rather than merely matching another copy of the same SOI data.

Run the dependency verifier:

python scripts/verify_dependency.py

The verifier:

  1. samples nine admitted filings with diverse structure and size;
  2. fetches each primary HTML filing from SEC EDGAR;
  3. reads identifier-matched fair value and principal facts from the document;
  4. compares those values with the committed panel; and
  5. checks the data release's NUM facts only when diagnosing disagreement.

Expected result:

match: 30
rounding_or_units: 0
panel_error: 0
source_error: 0
unresolved: 0

Open reports/spot_check.csv and choose one source_url. Confirm the displayed holding and value occur in the filing. The sample covers admitted filings only; it is not evidence that every excluded filing should be forced into the panel.

What could go wrong: using the panel's own SOI values for the "filing" side makes the test circular. The human-readable SEC document is the independent source in this step.

Goal: rebuild the complete pipeline, run the test suite, and consume the result through separate serving layers.

Run the complete contract:

Generate the compact API bundle:

python scripts/export_app_data.py

Run the local backend and static UI:

PYTHONPATH=. uvicorn app.api.main:app --port 8000
python serve_web.py

Open:

  • UI: http://127.0.0.1:3000
  • API documentation: http://127.0.0.1:8000/docs
  • Codelab: http://127.0.0.1:3000/codelab/

The public deployment uses the same separation:

  • Replit serves app/web/ and the generated static codelab.
  • Vercel serves the read-only FastAPI backend and compact JSON data.
  • app/web/config.js or the Replit LANTERN_API_BASE environment variable points the static UI at the backend.

The economic report in reports/economics.md states measured wall-clock values, its compute-rate assumption, and the linear scale extrapolation. Re-run the measurement on your own hardware before quoting speed as a universal result.

What could go wrong: the UI and API are intentionally deployable separately. If the UI loads but shows a network error, check the API base URL and backend CORS configuration before changing the data.

Positive : A correct full run leaves dvc status clean, the self-check at 10/10, and all tests passing.
